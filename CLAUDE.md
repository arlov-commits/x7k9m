# CLAUDE.md — Academic Planner (x7k9m)

Operating instructions for Claude Code working in this repo. Read this before making changes.

## What this is
A single-file academic planner PWA (`index.html`, vanilla HTML/CSS/JS, no build step) for one user. Tabs: Dashboard, Week (sprints), Syllabus, Tasks, Events, Notes, Season. Data persists to localStorage and mirrors to Supabase. Hosted on Cloudflare Pages, auto-deploys from `main`.

The exceptions to "single file" are the almanac (v9.0), the monastery calendars (v10.2) and the syllabus feed (v11.5): `almanac.js` (engine), `almanac-data.js` (name tables), `calendars-data.js` (published calendar tables) and `syllabus.js` (the .xlsx reader) load as separate scripts and are precached by `sw.js`. It drives the Season tab (solar terms, 候, moon quarters, earthly branch, Sun sign, Moon sign, Mercury sign with retrograde) and, in the Week tab, the solar-term pill plus moon quarters. In Season the two flanks **mirror** each other (v10.4): three parallel tracks a side, coarsest outside to fastest inside — west ☉ Sun / ☿ Mercury / ☽ Moon, east 建 branch / 節 term / 候 pentad — with a shared tonal ramp so a track's shade tells you its rate of change on either side. The nested container/sub-pill construction was retired with it. Because the running 候 lives in a lane now, the day cell shows a 候 or 節氣 **only on the day it opens**. `almanac.js` v1.3 adds the Moon's ecliptic longitude, checked by elongation against the moon-quarter fixtures rather than by a fixture of its own. Week and Season draw the same weeks and days on purpose — pressing the shared nav slot crosses between them at the same scroll position, which only works while their rows correspond. The crossing holds **the row the viewport is reading**, chosen as the first row not entirely above the fold, so a mid-row position anchors on itself instead of jumping to the next row down. `almAlignTo` is **self-correcting**: it measures where the row actually landed and nudges by the residual over the next few frames until two agree within half a pixel, so a reflow arriving after the scroll (`almFitLabels`, a webfont, the sticky flanks) cannot leave it off. Never replace that with a single computed `scrollTo` — that is exactly the bug it fixes, and the residual it absorbs is invisible until someone feels it. They are verified against `almanac-fixtures.json` by `test-almanac.html` + `test-almanac.js` (serve the repo over HTTP and open the page; expect zero failures). **Two 72 候 lists ship (v10.6), and the local one is the default:** `HOU_UKIAH` (優凱谷七十二候 v3.0, a phenological calendar for the Ukiah Valley — not a translation; Ukiah's year is close to the inverse of North China's) with the classical `HOU` selectable under Settings → Almanac. Both use the identical frame, so switching changes only names, never a date, and `HOU` remains what the fixtures verify. Every Ukiah entry carries a `desc` shown on hovering or tapping its 候 pill, and the Season header names which list is running.

**Everything in both flanks is tappable (v11.0)** and opens one shared reading card (`almPopOpen`): a 候 pill gives what you would actually see in those five days; a sign pill gives that sign read **for that planet** (☉ Leo and ☽ Leo are different statements, so each has its own text); a lane tag gives what the whole track measures, its rate, and its one salient fact; and the ℞ modifier — a target nested inside the Mercury pill, with propagation stopped — explains retrograde. A `title` carries the same text for a pointer, but the tap is the real affordance since a title is unreachable on a phone. Element and modality are **derived, never stored** (`almZodGrid`: element = i % 4, modality = i % 3, which are coprime, so all twelve pairings occur exactly once). The western lane cards and the retrograde card carry a caveat saying plainly that the astronomy is exact while the reading is a traditional attribution — keep it. `ALMANAC_SPEC.md` carries the provenance — read it before touching the data tables.

## The syllabus feed (v11.5)
The syllabus is **not in the codebase**. It is `calendars/source/syllabus.xlsx`, a spreadsheet the user maintains, read straight off the deployed site at runtime by `syllabus.js`. Drop a new file over that path, push, and the planner picks it up on the next load — a new term is a new file, not a new commit. Do not add a build step for it and do not generate a data file from it: `calendars-data.js` is generated because its sources are third-party CSV exports that need reconciling; this one has a single author and needs none. `tools/check-syllabus.js` only *reports* what the app will read — run it to see the counts and warnings before pushing, never to produce a committed artefact.

It is reference data, so it is **cached under its own localStorage key, never in `state`**, never in a synced collection, and the network is never in the critical path — the tab renders from cache and a refresh lands later. What is the user's own is the tick and the star, held in `state.sylMarks` keyed by the entry's id and synced as a profile singleton. **Ids are derived, not stored**: `-hash(alias|due|type|title|time)`, negative so they can never collide with `genId()`'s positive ids. Same row, same id, on every device — which is what carries a "done" tick across a re-fetch. Editing a row's title or date in the spreadsheet mints a new id and drops that row's tick; that is the accepted trade for having no id column to maintain by hand. A feed entry can be **edited in the app** (v11.9), but the spreadsheet still owns the row: an edit is kept in `state.sylEdits` as a **patch** of only the fields actually changed, keyed by the same derived id the ticks use, and applied over the feed row in `sylFeedEntries()`. Every field left alone keeps following the spreadsheet, which a copy of the row would not do; a field edited back to what the feed says stores nothing; and **Reset** (the editor's Delete button becomes it, plus a button on the row) drops the patch. A feed entry still cannot be deleted — the spreadsheet owns whether a row exists. `state.syllabus` holds only what the user adds by hand, and `sylAll()` is the single read path that merges the two. `sylDetailSrc()` is the one text a detail editor opens on and the table shows: for an unedited feed row that is the citation with the row's note appended, for an edited one it is what the user wrote — composing the note back on top of an edited detail is what would duplicate it.

Classes are whatever the workbook names — one sheet per class, `Full Name (Alias)` — so nothing about them can be hardcoded. They take colour **slots** `c0..c5`, aliased in one `:root` rule to accents each theme already defines; `var()` resolves at use, so a slot follows the active theme with no per-theme declarations. The slot order is chosen for separation in Ember, whose warm accents otherwise collapse together, and deliberately avoids `--accent-life` (Tasks) and puts `--accent-cn` last so a class never lands on the Tasks orange in the legend. A hand-added entry stores `clsAlias` alongside `cat`, and `sylRealignCats()` re-resolves the slot on every feed load, so reordering the sheets next term cannot silently re-file it. **No class is named in the code** (v12.0). The four tokens this app shipped with (`bh`/`wh`/`cn`/`ab` — spring 2026) are gone with the term they belonged to: `CAT_NAMES`/`CAT_SHORT` now hold only the three things that are not classes (Event, Task, Custom), and every category picker is filled from `sylClasses()` at open time by `fillCatSelect()` — never from markup, which is what went stale. A record still tagged by a retired class is **not rewritten**: `catName()`/`catShort()`/`catClass()` all fall back to Custom together, so it reads and draws as Custom wherever it appears (including its own column on the Dashboard, so a starred one cannot vanish), and its editor keeps the old tag as one explicit "Custom (from a past term)" option — choosing anything else is how the user clears it, deliberately. The `--accent-bh/wh/cn/ab` **palette tokens stay**: the class colour slots `c0..c5`, the almanac lanes and the monastery calendars all alias them, and they are colours, not class names.

**Records outlive the code.** Taking the class names out of the source does not remove entries already stored under them: those live in the synced collections and are the user's data. Settings → **Retired Classes** counts them and offers one sweep — a record whose `cat` is neither a workbook class nor one of the three live kinds, plus a hand-added syllabus entry due before the workbook's own first date (which is how entries filed under the still-live Custom bucket are caught). The date test is confined to hand-added syllabus entries: a task can be undated or long-running, so its date is no evidence of its term. It is skipped entirely while the feed has not loaded — a missing workbook must never read as "everything is old". Deletion goes through the ordinary array-removal path, so `detectAndQueue` writes one tombstone per record and it propagates; the section removes itself once nothing matches. Never purge these on load: they are the user's records, and clearing them is theirs to authorise.

**Nothing is seeded.** `defaultTasks/LifeTasks/Deliverables/Events/Syllabus` all return `[]`. A seeded collection is not inert here: on a device whose stored payload lacks the key, `applyChosenState` re-seeds it, the rows are given ids, and per-record sync pushes last term's demo data back to every device. `state.deliverables` is dead (nothing has rendered it since v11.5) but stays wired for sync so existing rows are not deleted under other devices.

A `_Recurring` sheet (any sheet whose name starts with `_` is not a class) holds **one row per repeating assignment**, expanded here into one entry per due date so the spreadsheet stays short and the app still shows the item on every date it is due. A skipped week is not numbered: `#5` is the fifth one actually due. Rows whose date or title does not parse are ignored, which is what lets the help text sit under the data on that sheet.

The spreadsheet defines the term: `sylAdoptRange` takes `semesterStart` and `maxFutureDate` from the feed's own date range, but **only when that range changes**, so a deliberate edit in Settings survives every later load. Feed text is spreadsheet text — escape it on the way out (`escHtml`); the syllabus title/detail render path escapes hand-added entries too, which is a fix, not a regression.

`calendars-data.js` (v10.2) holds the Abhayagiri and DRBA observance calendars as published, and is **generated** — run `node tools/build-calendars.js` over `calendars/source/*.csv` and commit both; never hand-edit it. Season tab only. Abhayagiri's "Alms Round" and its matching "<N> Moon Observance Day" are one occasion; the generator drops both and records the phase as `p`, so a date carrying a `p` **is** a Wan Phra day.

The Season day cell (v10.5) is a **centred column with two corners**. The corners carry the two badges — the moon top-left, `today` top-right — and everything on the centre line is centred: the date, the solar openings, and the event chips, the last divided off by a rule drawn only when there are events. Only an event chip's own text stays left-aligned, since a two-line title set ragged-centre inside its own ground reads worse than one with a straight edge. Nothing but an event is chipped, which is what makes an event unmistakable.

A starred syllabus entry is marked on **its own title cell**, never on the whole row: a day's entries share their class and due cells through `rowspan`, so a row-wide tint belonged to whichever row owned those cells — starring the first entry of a group bled the tint down the whole group and starring a later one left a hole across the middle.

A published event can be **mirrored to the Week tab** (v11.2): tapping its chip offers "Send to Week", which creates an ordinary all-day event carrying a `calRef` back to its source (`src|date|title`). The published table is read-only and is never touched — only the copy moves. Sending is inline, not a popup (v11.3): tapping a chip **arms** it and a `→` appears in a slot at its right edge; tapping the `→` sends it and the same slot becomes an `×` that cancels. The slot is on every chip at all times and never changes size — only its contents do, and an idle one is hidden with `visibility` so it keeps its width. **The pill must never change size when clicked or sent**; that is why the sent outline is an inset box-shadow rather than a border. Arming is transient (`_calArmed`), never persisted or synced, and a click anywhere off a chip disarms. A mirrored event is its **own kind of thing**, not one of the numbered event colours: in the Week tab it is drawn as its Season original — the tradition's emblem and accent, and the outlined ground an observance has there — while keeping the Week tab's own dashed chip silhouette so it still sits among the other events. Arming eases in; send and cancel replace the node, so the changed chip alone is marked `cal-flash` for one beat and animated in, then unmarked without another render. Honour `prefers-reduced-motion`. Items are addressed **positionally** (`calDayItems(src,date)[i]`), never by embedding a title in an `onclick` — several titles carry apostrophes, and `JSON.stringify` into a double-quoted attribute is exactly how the first attempt broke.

The moon is stated **once for all three reckonings**, not once per layer: agreeing sources group onto a single reading. Attribution is by **emblem only** — a stupa or a dharmachakra beside the icon; the source is never written out, and local is never labelled at all because local is the default. A phase is **named** only when it is a local quarter: the intermediate phases read fine from the icon and would otherwise put prose on four days out of five. The full sentence survives as the `title`. The three reckonings — local astronomical, Thai, Chinese — routinely disagree by a day and are deliberately **not** reconciled. Only the local layer is drawn between the quarters (waxing crescent and so on); the monasteries publish new/quarter/full and nothing else, so the intermediate phases are never attributed to them and never group.

## Week-tab pills (v11.7)
The **week header is a heading and nothing more** (v12.3): it does not take a dropped pill, offer to add one, or act as an allocation target, and there are no week-scoped tasks (`weekNum`) any more. A pill belongs to a day.

A day column is barely 150px wide on a phone, and every pill here is designed against that width. **A pill's title is always its own flex item, left-aligned** (`.evt-title`, `.syl-pill-title`, both `min-width:0`): a title too long for the column then wraps against a straight left edge instead of setting itself ragged around whatever precedes it, which is what made these unreadable before v11.7.

What a pill says *about* an entry — which class it is, when it runs — sits in a **zone of its own** (`.pill-zone`): a soft block of the pill's own accent, no border, no second typeface, no brackets. Both pill kinds use the same zone, which is what makes them one family, and because the ground is the accent the pill is already tinted with, a zone reads as the same object at another depth rather than something stuck on. The tint is `color-mix` on `currentColor` with a flat `--surface2` fallback declared ahead of it.

An **event** states its time in a zone at the end of its own title — "Go shopping 5–7pm", `evtWhen`/`fmtEvtClock`, minutes only when it is not on the hour and a meridiem the two ends share said once — never as a column ahead of the title, which took width the name needed. The zone sits **inside** `.evt-title`, so it flows with the text like a last word and can never be stranded on a line of its own. The name leads and the clock follows: `.pill-zone.evt-when` needs that specificity to set its own lighter weight, since `.pill-zone` is declared later in the sheet. It states the time on its **start day only**: an all-day event has none to state, and on the later days of a multi-day run the start has already passed. The pill does not wrap onto a second line; an emblem is narrow enough to leave the title its width. A mirrored calendar event's `×` sits in the pill's **top-right corner** with `padding-right` reserved for it, because a trailing button in flow lands stranded on a line of its own.

A **syllabus** pill carries no clock at all: an entry is due on a day, and the hour only crowds the title (it still sorts the pill and still reads in the tooltip). What it carries instead is a **tag** — the type's symbol, the class alias (`catShort`, the workbook's own sheet alias) in a zone, and the star if the entry has one — holding everything that says *which* entry this is apart from *what* it is. The alias is set in the UI's own sans at weight 600: a second typeface for it was tried and read as clutter. The pill wraps: where there is room the tag and title sit inline, and where there is not the title takes a line of its own at full width with the tag above it as an eyebrow. **Do not pin the title to a fixed flex-basis to force that break** — an intrinsically-sized pill then measures itself against the basis instead of its text, and short titles wrap while long ones stay inline, exactly backwards.

A syllabus pill's actions are **on the pill, never in a popup**: tapping it lifts a rail of three targets — highlight, complete, open in Syllabus — over the pill itself. The rail is absolutely positioned and overhangs the pill on every side, which is what lets a target be thumb-sized while **the pill keeps its exact footprint and the day row never reflows**; do not reach for an inline expansion instead. The armed key is `entry.id|date` (one pill per day of a multi-day entry, so tapping one day must not open the rail on the others), transient in `_sylActing` — never persisted, never synced, and cleared by a click anywhere off a pill. It is read back at render time, so the rail survives the re-render a toggle triggers and the button under the finger updates in place. **Completing dismisses the rail and highlighting does not**: the struck-through pill is the confirmation for the one and worth uncovering, while the lit button is the confirmation for the other. Writes still go through `toggleSylDone`/`toggleSylHL` — one per-record write each. A completed entry **stays in the week**, struck through where it sits (`getSylForDate` no longer filters `done`): the week is a record of what was due, not only of what is left, and nothing should vanish out from under the finger that ticked it.

## Nav slots (v11.9)
The navs hold four **slots**, each one button wearing one of two faces: Week/Season, Syllabus/Dashboard, Events/Tasks, Notes/Settings. Four slots cover all eight tabs, which is what retired the More sheet: it was a third press and a modal to cross for Notes or Settings. Pressing a slot while on either face flips to the other; pressing it from anywhere else returns to the face it is showing. Neither face of a pair is the "primary" and there is no default to fall back to — the slot keeps **whichever face you were last on**, which is why `switchTab` records it: arriving at a face by any other route (the More sheet, a syllabus pill's "open in Syllabus", the term ribbon) leaves the slot showing where you are. `applyChosenState` restores the same invariant on load, which is what carries a device that was last left on Tasks or Dashboard into the pairing. The faces (`weekSlot`, `sylSlot`, `evtSlot`) are per-device and **never sync** — they say where this device's nav is pointing, not anything about the plan. Adding a pair means one row in `NAV_SLOTS` and nothing else; only the Week pair carries the scroll-anchored crossing (`almSwapTab`), because only it draws the same rows on both sides.

## Find, and the two navs (v12.2)
The **side nav is the bottom bar transposed**: both render `NAV_SLOTS` through the same `slotBtn`, one cell per slot, `flex:1` dividing the full height so a fifth pair would need no layout change. The active ground sits on the `.nav-face` (the icon-and-label group), not on the cell — a cell a fifth of the screen tall filled with the active colour reads as a slab — and the cell keeps only the leading bar, which is the bottom bar's `border-top` rule rotated a quarter turn.

**Find** (`#findBar`) is pinned to the viewport, not to a tab, and lives outside `#app` with the back-to-top button: `render()` replaces that subtree wholesale and neither may lose its state mid-repaint. It exists because the browser's own Ctrl+F cannot work here — seven of the eight tabs are in the DOM but `display:none`. Matches are wrapped in `<mark class="find-hit">`; `findClear()` unwraps and `normalize()`s so the DOM returns exactly as it was, and `findReapply()` re-marks after every render. Matching **folds diacritics one character at a time** (`findFold`), so the folded haystack keeps the original's length and a hit's offsets still address the real text — this is what lets "surangama" find Śūraṅgama. Hidden subtrees are skipped by `offsetParent`, which is also what keeps the inactive tabs out of the marking pass; their counts come from `textContent` instead (`findTabCounts`). With **all tabs** ticked, stepping past the last match opens the next tab that has one; without it, stepping wraps inside the tab and never navigates. Enter/Shift+Enter step from anywhere inside the bar, not just the input — after ticking the checkbox the focus is on it, and a dead Enter there reads as breakage. On a **coarse pointer** the first Enter blurs the query (the keyboard is covering half the results) and lands on the match typing already selected, rather than stepping past it; the next Enter steps. On a fine pointer Enter always steps, as a browser's own find does.

Everything in the bar except the query field is a **control, not text**: `user-select:none`, no callout, and `touch-action:manipulation` so a quick second tap on next/prev is another press rather than a double-tap zoom (which was expanding the page and pushing the close button off the edge). The query field is 16px on a coarse pointer — under that a phone zooms the page when it takes focus — and nothing in the bar calls `focus()` on a touch device, since that is what was raising the on-screen keyboard when you only meant to tick "all tabs".

## The shell (v12.5) — no fixed chrome, one scroller
**The app is a column exactly one viewport tall** (`.shell`, `height:100dvh`) holding three things: the find bar, `.frame` (a row: the desktop rail and `#scroll`), and the tab bar. **Nothing in the chrome is `position:fixed`, and nothing may become so.** A bar fixed to the bottom is positioned against the *layout* viewport, which on a phone is not the viewport you can see — Chrome on Android keeps the taller URL-bar-hidden height there — so the bar hung below the screen with its labels cut off. Two attempts to correct that from JS both failed and are worth remembering: computing the overhang from `documentElement.clientHeight` assumed which of several viewport heights is reported there (wrong on a real phone, so nothing moved), and measuring the bar's own rect against `visualViewport` lost to the compositor, which moves fixed elements itself during a fling — that one parked the bar mid-screen. In flow at the foot of a `100dvh` column the bar cannot be anywhere but on screen: no listeners, no correction, no race, and the whole class of bug is gone rather than guarded against.

The **only scrolling element is `#scroll`** (`scroller()`); the document does not scroll. Anything that reads `scrollY` or calls `scrollTo` drives that instead — `almAlignTo`, back-to-top, the find bar's `scrollIntoView`. `#app` is repainted wholesale by `render()`, `#scroll` is not, so the scroll position survives a repaint. The navs are their own elements (`#sideNav`, `#bottomNav`) with only their contents rewritten, so they hold their place in the layout. Sticky descendants (the almanac flanks) now stick to `#scroll`, which is the same visual result.

The cost, stated plainly: the browser's URL bar no longer auto-hides while scrolling, because the document itself no longer scrolls. It does not apply at all once the app is installed to the home screen.

**Back to top** appears after exactly **three screen heights**, in every tab (`TO_TOP_SCREENS`). A threshold derived from the document's own height moves with the tab you are in, so the button appeared at a different point in each and read as unpredictable. Its state is settled three ways, because a scroll handler throttled to one reading a frame is right for a finger and wrong for a programmatic scroll — a smooth scroll ends at a definite moment, and a frame pending at that moment takes the last reading mid-flight and leaves the button on screen at the top of the page. So: the press hides it and locks out readings until it lands (a finger scrolling the other way breaks the lock at once), `scrollend` settles it where the browser has that event, and a late re-check covers the browsers that do not.

## Nothing may widen the page (v11.9)
One unbreakable token — a URL pasted into a syllabus row — used to stretch a day column past the viewport, scrolling the whole layout sideways under a bottom bar that is fixed to the viewport, which is what made the tab bar look misplaced and cut off. Two defences, and keep both: text that can carry a URL breaks anywhere (`.evt-title`, `.syl-pill-title`, `.syl-title-text`, `.syl-detail-text`), and `body{overflow-x:clip}` holds for whatever comes next. `clip`, not `hidden`: it does not make the body a scroll container, so the almanac's sticky flanks keep sticking. Where a cell may hold long text, the column that must give way is named explicitly (`.syl-title-cell{width:100%}`) — otherwise the title column is the one that yields and collapses to a few characters a line.

A week pill's title is capped at **ten rendered lines** (`sylFitTitles`, `SYL_PILL_LINES`), and what comes out is the **middle**, not the end: the opening says what the reading is, the closing usually carries the page range. The full text stays in the Syllabus tab and in the pill's `title`. Ten *rendered* lines is why this measures rather than counting characters — the same entry is four lines on a desktop row and twenty on a phone, so the cap never bites on a wide screen and no media query decides it. Two passes (restore, then measure) like `almFitLabels`, so a render costs one layout, not one per pill; only an oversized pill pays for the binary search.

## Deploy workflow (NON-NEGOTIABLE)
- **Never commit directly to `main`.** A live user depends on `main`.
- Work on a branch. Push the branch → Cloudflare builds a **preview URL** automatically.
- The user tests the preview URL on PC + phone, then merges the PR to `main` to ship.
- When you finish a task: push the branch and tell the user the exact branch name and that they need to open the PR and merge it. Do not assume merged.
- Branch naming: `claude/<short-description>`.

## Versioning
- Version lives as an HTML comment on line 1: `<!-- Academic Planner vX.Y -->`, and in a visible `.version-label` in the header, and in the service worker `CACHE_NAME`.
- **Bump the version on every commit** (patch bumps for fixes, minor for features). Current: v12.6. All three locations must match.
- Bumping the SW `CACHE_NAME` every change is required or installed devices serve stale code.

## Architecture rules (hard-won — do not violate)
- **localStorage is the source of truth for the UI.** The network is never in the critical path of a user action. A tap/keystroke must never block on a fetch.
- **NEVER do whole-state last-write-wins.** Do not overwrite the whole remote blob with one device's whole local blob, and do not replace the whole local state from a remote payload. This silently destroys cross-device edits. (See SYNC_REFERENCE.md.)
- Sync reconciliation is **per-record, by immutable client-generated id**, with a DB-owned `updated_at` and `deleted_at` tombstones. Merge by id; never wholesale-replace arrays.
- Re-renders must not clobber in-progress user input. Never swap the entire state object out from under an open editor/text field mid-typing.
- Per-device cosmetic prefs (theme, UI modes) stay in localStorage and are NEVER synced. Only data-meaningful state syncs.

## Service worker
- Bump `CACHE_NAME` every meaningful change.
- `install`: cache shell, `skipWaiting()`. `activate`: delete old caches, `clients.claim()`.
- Registration side: loop-guarded `controllerchange` reload (reload once when new SW takes control; guard with a flag; skip first install) so a refresh lands on new code.

## When unsure
Prefer the smallest correct change. If a change touches sync/persistence, follow SYNC_REFERENCE.md exactly. Ask the user before any destructive data migration.
